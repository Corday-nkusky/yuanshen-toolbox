## 已知边界（不算 bug，但要知道）

- **自动上传只跟元扫雷**：阿比特目录是手动加的、可能混着别人的录像，所以 `.avf` 不自动传。
      「全部完成局」也不在自动上传的范围里 —— 那不是「符合要求」，是备份，量级完全不同。

- **重复副本判重靠字节相同**。阿比特若改格式，让 `HI-SCORE *.avf` 与正本字节不同，就抓不到
  （那时得改成比对点击流签名，成本高一个量级）。当前 479 个 HI-SCORE 里 395 个的孪生字节全同。
- **阿比特文件名解析只覆盖实测写法**（`HI-SCORE ` 前缀、`_NF_`/`_FL_`、`#Exp_`、`Beg_1.00_3BV=6_...`）。
  `玩家名在前` 那种（`Ju Ze En_Exp_26.1(3bv123).avf`）解析不出，靠录像内容兜底 —— 也因此
  「无法解析」计数里可能出现其实是正常的文件。
- **扫描目录上限 20000 个子目录**，到顶截断并在状态栏说明；正常 replay 目录不会触发。
- **扫描缓存不做孤儿行剪枝**：删掉的录像会在 `scan-cache.db` 里留行（不影响结果，只是库慢慢变大）。
- **带比赛编号的标识要先登记**：打比赛产生的录像（元扫雷、阿比特都一样）标识后面会带
  比赛编号（如 `玩家名(地区) G18248`）。这种完整标识若没在账号「标识管理」里登记，
  上传会成功但 `state=d`（标识不匹配、不进榜）。程序只能提前标红，不能代登记。
- **`record.ini` 对账只覆盖元扫雷**：那份文件是元扫雷写的，阿比特的成绩没有第二来源可校准。
- **「手动添加 = 全是你自己的」是约定，不是校验**：程序只能靠目录边界判断归属，加进来的目录
  里若混着别人打的录像，仍会计入 PB 并进上传列表。没有做「按 `player_identifier` 白名单过滤」
  —— 同一个人在不同软件不同时期的标识写法实测能变出八九种（拼写、大小写、地区、编号、有没有
  括号都不一样），白名单会误杀自己；而下载来的录像里那个名字字段是可以被本地 profile 改写或
  冒用的，也不能当证据。
- **首扫时长取决于录像条数**：2 万局、冷缓存约 3 分钟（`read_video` 逐局重演），
  有进度条但不是能加速的东西。缓存命中后 1 秒出头。
- **头部正常的半截录像仍可能带崩进程**：`core.looks_like_video()` 只看前 3 个字节，
  能挡掉全零 / 别的格式，但元扫雷正在写、写到一半的 `.evf` 头部是完整的，送进
  ms-toollib 仍可能硬崩。根治要把 `read_video` 放进子进程（崩溃只死子进程），
  代价是每题 20~40 ms 的进程启动开销 × 2 万局，目前不划算；`Tracker` 的「写稳 1.5 秒」
  已经挡住自动上传这条路的常见情形，扫描本身还有窗口。

## 功能待办（等需求确认）

- [ ] **网站数据磁盘缓存**（2026-11-14 提出，判定为「棘手，以后再做」）。
      **现状**：登录态已持久化（`openms.json` 存 DPAPI 密文的 session_id，站点每次请求续期，
      90 天），所以不需要每次重登；但**网站数据零缓存**，每次启动、点「刷新网站记录」、登录后、
      上传结束 0.4 s 后都全量重拉。实测启动到录像列表就绪约 12 s，其中 10 s 花在
      `videolist` 之后补明细：2068 条 / 每批 100 个 ID / 站点限流 5 次每秒故串行留 0.25 s
      → 21 批。本地 `scan-cache.db` 只缓存**本地录像解析结果**，与网站无关。
      **要做的**：把 PB / Top5(+明细) / 标识 / 录像列表连 `user_id` 与拉取时间落到
      `site-cache.json`，启动先渲染它，真实数据到了再替换。
      **硬约束（不做就等于引入 bug）**：
      （a）缓存**只能用于显示**，绝不能参与「网站是否已有这条录像」的判定 —— 用户在网页上
      删掉的录像若留在缓存里，上传会被永久跳过，再也传不上去。判定的权威来源仍然只能是
      真实 `videolist`+明细，`oms_synced` 对缓存数据必须保持 False。
      （b）换账号（`user_id` 不同）必须整体作废，不能把上一账号的 PB 显示给新账号。
      （c）上传结束后的那次重拉若失败，缓存要标成「不确定」而不是继续显示旧值。
      **待定**：界面上要不要说明「显示的是上次的记录，正在更新」。若要写，只能写用户视角
      （如「正在读取最新的网站记录…」），不许出现缓存/文件名字段名一类实现细节。

- [ ] **阿比特批量混传**：只在真账号上单条试过（1 条，state=d），没跑过「元扫雷 + 阿比特混在一起传几十条」。
- [ ] **表格列宽/对齐的可配置化**：现在对齐按「数字右、短标签中、文本左」写死在 `cols` 里；
      真有人抱怨再抽成配置。
- [ ] **导出 CSV 覆盖范围**：目前只导 PB 表，前端成绩的三个 Top5 表没导。

## 每次发版前的手工验收

1. `python test_arb.py`、`python test_resume_ui.py`、`python test_retry.py`、
   `python test_smoke.py`、`python test_upload.py`、`python test_site_pb.py`、
   `python test_mode.py`、`python test_autoup.py`、`python test_mslaunch.py`、
   `python test_record_ini.py`、`python test_auto_flow.py`
   退出码都是 0（`test_tabs.py` 是截图工具，不参与回归判定）。
2. `build.cmd` 会自动把 `dist\YuanshenToolbox.exe` 部署到
   `%APPDATA%\Metasweeper3.3.4\`；在里面运行 `--probe` → 日志里
   `启动 YuanshenToolbox vX.Y.Z` 与 `APP_VER` 一致；文件属性 → 详细信息里的 FileVersion 也一致。
3. 真机开一次：概览 / PB / 前端成绩 / 上传四页各看一眼（行高、对齐、滚动条）。
4. 有账号时确认「网站已有 N」与站点实际条数一致（去重键没漂）。
