# PB 表改版调研：从「204 行列表」到「3BV 网格」

> 调研时间：2026-11-16
> 对象：openms.top 的个人 PB 页（`/#/player/3/pb`，player 3 = 你本人的账号）与其前端源码
> 目的：搞清楚它为什么比我们的列表好用，并给出能落进 Tkinter 工具箱的展示方案
> 事实分级：**【源码】**= 读过 `_ms/saolei_website` 代码；**【实测】**= 我实际发了请求、算了数；**【推断】**= 由前两者推出，未直接验证
> **落地状态**：已按第 4 节实现（`app.py` 的 `PBGrid` + `_build_pb`，`openms.py` 增 `pb_counts()`），下面第 4 节的细节以代码为准，与本报告有出入的地方（例如详情条紧贴网格、格子自动收缩高度）都是实现时调整过的。

## 0. 结论

1. **列表失败不是排版问题，是把函数画成了字典。** PB 的本质是「BV → 成绩」这个定义域上的函数，BV 是从 1 开始的**离散整数**。列表把每个点摊成一行 KV，读的人必须自己在脑子里重建坐标轴——而人脑重建不了 127 个点。openms 只是把这个函数**按它本来的坐标画出来**：行 = BV 十位段，列 = 个位。【源码】
2. **拿走的不是配色，是四个机制**：BV 当坐标、空缺显式化、同级内可比、格子即入口。热度配色我建议**不抄**，用我们自己的级别主色三档就够。【推断】
3. **我们缺的最值钱的一列是排名，而且它是免费的**。站点 PB 接口每条带 `rank`，`/pb/counts` 一次请求给出所有小榜**分母**。你现在本地 204 行、并上网站后 210 行，其中 **207 行的排名能直接对应**（132 同速 + 69 网站更快 + 6 仅网站），只有 3 行是本地独有、没有排名。【实测】
4. **成本可控**：一个 `tk.Frame` + Label 复用池，切级别只改 text/底色，不重建控件。数据层几乎不用动——`core.merge_site_pb` 已经把 `site_rank` 放在每一行里了，只差一个小榜人数。【源码】

## 2. openms 怎么做的（源码级）

### 2.1 结构

`front_end/src/views/UserView/UserPBView.vue`

- 顶部一排控件：`NF` 勾选框 + 指标按钮组（`time` / `bvs` / `stnb` / `rank`，默认 `time`）+ 刷新。
- 主体：`<PBRecordGrid v-for="level in pbLevels">` —— **三个级别各一张网格，竖向堆叠**，不是切换。
- 一次请求 `GET /api/speedranking/pb/player/{id}` 拿回全部记录，前端不再请求。

`front_end/src/views/UserView/PBRecordGrid.vue`

- 网格 `grid-template-columns: 4.5em repeat(10, minmax(4.3em, 1fr))`，`grid-auto-rows: 25px`。
- 第一行是列头 `0..9`；每行首列是 `10–19`、`20–29` 这样的范围标签。
- 行范围按**有记录的最小/最大 BV** 动态算：`range(floor(min/10)*10, floor(max/10)*10, 10)`。没有记录的行整行不出现。
- 单元格内容 = 当前指标的值（`formatPBValue`）；`cellStyle` 按值取色阶；`recordTitle` 把 BV、三项指标、排名塞进 hover 提示；格子里的文字是录像链接（点开预览）。
- 空位置：`<span class="pb-cell" />`，只有一个描边，没有内容。

### 2.2 派生指标在前端算

`services/pbRankingService.ts:34-38`

```
time → ms_to_s(timems)
bvs  → bv / (timems/1000)
stnb → COEF[level] * bv / (timems/1000) ** 1.7      COEF = {b:36, i:162, e:435}
```

接口只返回整数毫秒，三个指标客户端自己算。**我们已经是这个结构**（`core.stnb_of`），不用改。

### 2.3 着色：分段色阶，阈值按级别

`utils/config.ts:44-62`

- 通用调色板 28 色（灰→紫→红→绿→蓝→橙→粉→青→亮绿，Excel 条件格式风格）。
- 阈值不是手填的，是同一套 `0.5 → 8` 的刻度线性变换出来的：初级 `12-2v`、中级 `30-4v`、高级 `90-10v`；色板倒序配对，使更快的时间取到更亮的颜色。
- `stnb` 阈值 = `bvs` 阈值 × 25。
- 排名另有一套：`['#FFC000','#A0A0A0','#CD7F32', 蓝22%, 蓝14%, 蓝7%, 透明]` 对应 `[1,2,3,10,50,100]` —— **金银铜 + 三档浅蓝**。

这套东西的信息价值在于「同一级别内可比」，代价是 28 色肉眼分辨不了那么多档。

### 2.4 排名从哪来

`/api/speedranking/pb/player/{id}` 每条返回 `{level, bv, nf, timems, video_id, rank}`。【实测】

`/api/speedranking/pb/counts` 返回 `{"std:b:17": 132, "nf:b:17": ..., ...}`，即每个小榜人数 —— **就是 rank 的分母，一次请求拿全**。【实测】

我抽查了两条，rank 与榜上位置、count 完全吻合：

| 小榜 | 你的记录 | rank | 榜人数 | 榜上第 rank 位 |
| --- | --- | --- | --- | --- |
| std b:17 | 2640 ms | 43 | 132 | player 3，2640 ms ✓ |
| std e:150 | 57060 ms | 79 | 111 | player 3，57060 ms ✓ |

口径（`back_end/saolei/speedranking/PB_PLAN.md`）：std 榜**包含 NF 录像**，nf 榜只收 `right_ce == 0`。跟我们的「全PB / NF PB」两榜口径一致。【源码】

## 3. 我们从里面拿走什么

| 机制 | openms 的做法 | 我们怎么用 | 为什么重要 |
| --- | --- | --- | --- |
| **BV 当坐标** | 行 = 十位段，列 = 个位 | 同 | 位置固定后，第二次看不用重新找 |
| **空缺显式化** | 空 `<span>` 只有描边 | 底色更浅 + 中央一个点 | 高级缺 40 个，这是最该被看见的信息 |
| **同级内可比** | 28 色分段色阶 | **三档**（见 5.3） | 一眼看出哪段弱，不用逐个读数字 |
| **格子即入口** | 点开录像预览 | 单击出详情条，双击在资源管理器定位 | 我们的是本地文件，比网页更有优势 |

**不拿的三样**：28 色彩虹（分辨不了）、三级别竖向堆叠（我们窗口高度不够，见 5.1）、网页录像预览（本地文件直接开）。

### 4.3 着色：三档，用我们自己的级别色

三级已经有主色，直接拿来做深浅，切级别时整页色调跟着变：

| 级别 | 最深 | 中间 | 最浅 | 空缺 |
| --- | --- | --- | --- | --- |
| 初级 | `#ff6f9c` | `#ffa8c4` | `#ffe4ee` | `#f7f2f7` |
| 中级 | `#3fa9dd` | `#8fcbe9` | `#e0f3fd` | `#f7f2f7` |
| 高级 | `#8f6ce8` | `#bda6f3` | `#ebe4fd` | `#f7f2f7` |

深档上白字，中/浅档上 `#3c3352`。

**档位怎么切**（推荐顺序）：

1. **排名百分位**（默认，需要登录）：`rank/count` ≤ 10% 最深、≤ 35% 中间、其余最浅。含义是"你在全国这个 BV 上的位置"，跨 BV 绝对可比。阈值是估计值，实现时按你的实际分布再调（你现在 132 人的小榜上排 43，落在中档）。
2. **本级 3BV/s 分位**（未登录时）：本级有成绩的格子里前三档，按 1/3 分位切。含义是"你自己哪段强哪段弱"，相对可比。
3. **不着色**（两边都没有）：只画描边。

为什么不做成渐变：一屏 140 格里，人能分辨的深浅不超过 4 档；28 色那种"看起来专业"的配色，实际读数是不可用的。

### 4.5 空缺和门槛

- **空缺**（该 BV 没有成绩）：最浅底 + 中央一个 `·`。不写"暂无"（140 个格子写 40 个"暂无"是噪音）。
- **低于官方门槛**（初级 BV < 10、中级 < 30、高级 < 100）：数据照常显示，但格子加一圈虚线描边。初级现在有 8 个这样的位置（BV 2–9），它们多半是运气局，跟 BV 14 的 1.9 秒不是一类成绩。**只做视觉区分，不删、不排序、不提示**。

### 4.6 技术实现

**控件选型**：`tk.Frame` + Label 复用池，不用 `ttk.Treeview`。

理由：Treeview 只能整行着色（`tag_configure`），做不到逐格上色，这是硬限制。而 `Canvas` 画 140 个 `create_text` 更快，但文本对齐、DPI 缩放、点击命中判定都得自己算，改一次字体就要重排。

做法：

```
class PBGrid(tk.Frame):
    _pool: list[list[tk.Label]]     # 按最大尺寸建一次，(14+1) 行 × (10+1) 列
    def bind_data(self, rows_by_bv, metric, tone_fn): ...   # 只改 text/bg/fg，不 destroy
```

- 复用池按 **14 行 × 11 列**（1 列行首标签 + 10 数据列，1 行列头）建一次，约 165 个 Label。
- 切级别 / 切指标 = 遍历已有 Label 改 `config(text=, bg=, fg=)`，多余的 `grid_remove()`。**预计 20 ms 内**（165 个 Label 的属性更新），这是推算、没实测。对比现在的 `Table._redraw()` 每次 204 行 `delete` + `insert`。
- 行高用 `sc(26)`，宽度交给 `grid_columnconfigure(weight=1, uniform="pb")`，窗口缩放自动跟。
- 数据层：`self.pb_rows` 已经是合并好的 204 行，`render_pb` 里改成按 `(level, bv)` 建字典再喂给网格。**不需要改 core。**

**新增字段**：`site_rank` 已在行里，只需再加一个 `count`（从 `/pb/counts` 取一次，与 `site_pb` 一起缓存）。`openms.py` 里加一个 `pb_counts()` 方法，跟 `pb_records()` 同一个请求周期。

### 4.7 保留的东西

- CSV 导出：按网格顺序导出（BV 升序，一行一个 BV），列名换成实际字段，不导出"级别/风格"这种恒定列。
- 搜索：保留，改成高亮而不是过滤（过滤后网格会出现"断层"，反而看不懂）。
- 「重新扫描」按钮：保留。

## 5. 明确不做的

| 不做 | 原因 |
| --- | --- |
| 三级别竖向堆叠（openms 的做法） | 28 行 × 26px = 728px，主区放不下，等于把列表换个形状继续滚 |
| 28 色分段色阶 | 超过 4 档人眼读不出来，且色板越大越难和谐 |
| 单行热力条（381 个 BV 挤一行） | 只能看颜色不能看数字；高级 127 个 BV 挤在 680 px 里每个不到 5 px，点击命中都困难 |
| 格子内嵌录像预览 | 本地文件，双击交给系统更快 |
| 任何"你的短板是 X，补上能涨 N 分"的提示 | 网格的职责是把分布画出来，结论由看的人下 |

## 6. 待你决定的三件事

1. **级别是否必须单选**。我倾向必须（4.1 的理由）；如果你希望保留"全部"，那网格只能给当前选中的级别，全部视图退回列表——两套 UI 并存会变复杂。
2. **默认指标**。我倾向「时间」（跟现在一致），颜色用排名百分位。也可以默认「排名」，那时格子里就是 `43/132`。
3. **低于门槛的格子怎么标**。虚线描边 / 直接不显示 / 正常显示。我倾向虚线描边。

## 7. 我没验证的部分

- **没有看到线上真实渲染**。本机没装 Playwright/Puppeteer，站点是 Vue SPA，`WebFetch` 拿不到渲染结果。所有关于 openms 视觉的判断都来自源码（`PBRecordGrid.vue` 的 grid 定义、`config.ts` 的色阶）和一次我按源码规格自己画的示意图，**不是你屏幕上那个页面的截图对照**。
- **没有打开过你的工具箱截图对照实测**。第 1 节的列数、行数来自 `shot_pb.png` 与 `app.py` 的 `_build_pb`，行数 204 是我从 `scan-cache.db` 重算的 PB，可能与界面当前显示（"仅显示本地"、未登录状态）不一致。
- **Label 复用池的性能是推断**。165 个 Label 的属性批量更新耗时没实测；如果超过 50 ms，切指标会看出卡顿，退路是改 Canvas。
- **排名直接可用的结论是快照**。今天 0 条本地更快，你下次没上传就破 PB 时，那几行的 `site_rank` 会与显示的本地成绩脱节——实现时必须判 `source`：`local` 行若本地更快，排名显示 `—`，不能标成那条成绩的名次。
- `counts` 接口的更新时机没查（是否会落后于 `rank`）。如果两者不同步，`43/132` 可能出现分母暂时偏小。
