## 0. 一句话

新增第 6 个页签「每日」：把本机所有完成局按**打的那一天**聚合，一天一行 ——
局数、起止时刻、当天最快 / 平均 / 最慢的时间与 3BV/s；级别单选；点开某一天能看当天每一局并播放。

---

## 1. Arbiter 那张表在算什么

从截图 21 行数据反算，十列的真实含义如下（**【反算】**）：

| 列 | 含义 | 反算依据 |
|---|---|---|
| Date | 录制日期 | — |
| Games | 当天该级别的完成局数 | — |
| From / Till | 当天首局开始 → 当天末局结束 | 05.08.2022 两局，起 00:04:50 止 21:51:51 |
| Best / **平均** / Worst（时间） | 当天最快、**算术平均**、最慢 | Games=2 的四行 `(226.80+356.40)/2 = 291.60` 精确吻合；Games=1 的七行三值全等 |
| Best / **平均** / Worst（3BV/s） | 同上 | `(0.76+0.56)/2 = 0.66` 吻合 |

**中间那列是算术平均，不是中位数**。照抄这个口径 —— 否则同一批录像我们算出的数会和
Arbiter 不一致，玩家第一反应是"你这算错了"。

另外三点**【推断】**：按级别分开统计；不过滤 3BV 门槛（小盘刷出的高 3BV/s 照样进 Best）；
只显示有局的天，不补空白天。

## 3. 时间从哪来（全案地基，写错会静默出错）

`.evf` 和 `.avf` 的录像头里都带开始/结束时间戳，`ms_toollib` 直接给：

```
EvfVideo.start_time / end_time
AvfVideo.start_time / end_time     # 整数，单位是**微秒**（1e15 量级），不是毫秒
```

**【实测】23532 个录像（23183 avf + 349 evf）全部合法**：无 0、无负数、无未来时间，无一个解析异常。

### 3.1 两种格式的语义不一样

| 格式 | 时间戳的语义 | 正确读法 | 与文件 mtime 的偏差【实测】 |
|---|---|---|---|
| `.evf`（元扫雷） | 真 UTC epoch 微秒 | `datetime.fromtimestamp(us / 1e6)` | 中位 **0.07 s**，最大 1.9 s（349/349 全部吻合） |
| `.avf`（阿比特） | **当时的本地墙钟**被直接当成 UTC 写进去 | `datetime.fromtimestamp(us / 1e6, timezone.utc).replace(tzinfo=None)` 得到的 naive 值就是本地墙钟 | 中位 **0.03 s**（23181/23183 吻合） |

为什么两种？【推断】元扫雷用了真 UTC 时间戳，阿比特把本地时间结构体直接当 epoch 写。
两者都能和文件 mtime 对上，说明这就是它们各自的写法，不是数据损坏。

### 3.2 归一化：读进来就统一成"真本地 epoch 秒"

上层（聚合、渲染）从此不必知道 avf/evf 的差别：

```python
def _wall_epoch(us, src):
    """录像内时间戳 → 本机时区的真 epoch 秒。

    .avf 存的是「当时的本地墙钟」，被当成 UTC 编码：先按 UTC 读回 naive 墙钟，
    再 timestamp() 让本机时区把它解释成真 epoch。.evf 本来就是真 UTC，直接转。
    """
    if src == "arb":
        dt = datetime.fromtimestamp(us / 1e6, timezone.utc).replace(tzinfo=None)
    else:
        dt = datetime.fromtimestamp(us / 1e6)
    return dt.timestamp()
```

之后所有地方只用 `datetime.fromtimestamp(t0)`，永远正确。

### 3.3 反例：avf 用错读法会怎样

拿 `D:\扫雷\#Exp_4.73_3BV=191_3BVs=4.01_Anonymous.avf` 这局，真墙钟是
`2024-08-27 17:33:18`（文件 mtime 17:33:28，差 10 秒）。若对 avf 直接 `fromtimestamp`：

```
正确  utc-fromtimestamp + naive → 2024-08-27 17:33:18
错误  fromtimestamp            → 2024-08-28 01:33:18   ← 整整 +8 小时，跨日
```

后果是**所有 21:00 之后打的局被算到第二天，00:00–08:00 打的局被算到前一天**，而界面上
完全看不出异常 —— 只是"某天局数多了一倍、某天少了一半"。

### 3.4 守住它的单测

用两个真实样本各断言一次，**期望值写死成日期与时刻的字面量，不用 mtime 反推**：

| 样本 | 断言 |
|---|---|
| `%APPDATA%\Metasweeper3.3.4\replay\i_0_38.353_66_1.721_Corday(Tongcheng).evf` | `date == "2026-11-12"`，开始 `21:27:00` |
| `D:\扫雷\#Exp_4.73_3BV=191_3BVs=4.01_Anonymous.avf` | `date == "2024-08-27"`，开始 `17:33:18` |

第二个是防回归的关键：读法一改错，它立刻变成 `2024-08-28`。

### 3.5 已知边界

1. **`.evf` 在别的时区录制会偏**：`fromtimestamp` 用的是"现在"的时区，不是"录制时"的。
   中国无夏令时、他也不换时区，当前不会触发；写进未验证清单。
2. **录像头损坏 / 老格式无时间戳**：`t0` 取不到就退回 mtime，并在 `info["retimed"]` 计数，
   状态栏一句「N 局按文件时间归日」。实测 23532 个样本没有一个走到这条路。

## 4. 数据层设计

### 4.1 `core.read_video()` 增加两个字段

```python
"t0": _wall_epoch(v.start_time, src),   # 开始时刻，真本地 epoch 秒（float）
"t1": _wall_epoch(v.end_time, src),     # 结束时刻，同上
```

两边都包 `try/except`：取不到就给 `None`，让 `scan()` 兜底，**不让一个坏录像带崩扫描**。

### 4.2 `core.scan()` 落字段

```python
t0 = (vid or {}).get("t0")
if not t0:                       # 老缓存 / 读不出 → 退回文件时间
    t0 = mt
    info["retimed"] += 1
rec["t0"] = t0
rec["t1"] = (vid or {}).get("t1") or (t0 + rec["time"])
rec["date"] = datetime.fromtimestamp(t0).strftime("%Y-%m-%d")   # 取代现在那行
```

`rec["date"]` 由此变成**真实录制日期**，概览页「最近完成局」的日期/时间列顺手一起变准
（同一个字段，不必额外改界面）。

### 4.3 缓存迁移：老缓存里没有 `t0`

`scan-cache.db` 现在存着 23183 行没有 `t0` 的结果。**已定：一次性补全。**

- 扫描时发现缓存命中但缺 `t0`，就地重解析并写回；
- 首次代价实测 **30 秒**（23183 局，含缓存写回；Defender 全盘扫时会慢）；
- 那次扫描的状态栏写「补齐 N 局录像时间」，进度条照常走；之后永不复发。

### 4.4 新聚合函数（纯函数，可单测）

```python
def daily_rows(games, level=None, bv_min=0):
    """按天聚合，返回按日期倒序的行。

    每行：date / games / t_from / t_till / best / avg / worst /
          bvs_max / bvs_avg / bvs_min / nf / best_path / span
    """
```

- `games` 已经过既有过滤（只含完成局、标准模式），这里不再筛。
- 一天的定义：**本地时区 00:00–24:00，按开始时刻归日**（跨午夜的局算在开始那天）。
  实测去重后 22723 局里只有 **15 局**跨午夜（0.07%），不影响统计，但定义要写死。
- `t_from` = 当天最早一局的 `t0`；`t_till` = 当天最晚一局的 `t1`。
- `avg` 用算术平均（见 §1）。
- `best_path` 给"双击播当天最快那局"用。

```python
def daily_games(games, date, level=None):
    """某一天的局，按时间倒序 —— 给明细用。"""
```

### 4.5 性能：所以不做任何范围筛选

**【实测】本机 23183 局：**

| 动作 | 耗时 |
|---|---|
| 按天聚合一整个级别 | **1.2 – 7.1 ms** |
| 667 行 × 10 列插入 Treeview（首次 / 重插） | **13.8 ms / 5.7 ms** |
| 切一次级别（聚合 + 重画） | < 25 ms |

行数上限就是"有局的天数"：初级 302 天、中级 600 天、高级 186 天（含元扫雷）。
**所以页面不做任何时间范围筛选，一屏之外滚动即可** —— 加"近 30 天"只会让
"我总共练了多少天、从哪天开始"这个最重要的信息凭空消失，而它一点也不省时间。

## 5. 界面设计

位置：导航栏「概览」之后插入「每日」，变成 6 个页签（nav 右侧还有大段空白，放得下）。

```
┌─ 每日 ────────────────────────────────────────────────────────────────┐
│ [初级] [中级] [高级]                              600 天 · 10444 局      │
├───────────────────────────────────────────────────────────────────────┤
│ 日期        局数   起        止        最快     平均     最慢   最高  平均  最低 │
│ 2026-11-16   37   21:02:11  23:58:03  16.741  19.482  24.120  3.383 2.98 2.41 │
│ 2026-11-15  102   09:14:02  23:41:55  15.982  18.771  23.004  3.512 3.05 2.55 │
│ …                                                                      │
├───────────────────────────────────────────────────────────────────────┤
│ 2026-11-16 · 37 局 · 最快 16.741 s @BV50 · 跨度 2 小时 56 分            │
└───────────────────────────────────────────────────────────────────────┘
```

### 5.1 列定义

| 列 | 宽 | 对齐 | 格式 | 说明 |
|---|---|---|---|---|
| 日期 | 94 | center | `YYYY-MM-DD` | 倒序，最新在上 |
| 局数 | 48 | e | int | |
| 起 / 止 | 70 ×2 | center | `HH:MM:SS` | 跨午夜时止 < 起，原样显示 |
| 最快 / 平均 / 最慢 | 70 ×3 | e | `f3` | 秒，3 位小数 |
| 最高 / 平均 / 最低 3BV/s | 70 ×3 | e | `f3` | |
| 最高 / 平均 / 最低 stnb | 58 ×3 | e | `f2` | 越大越好，与 time 反向 |

十三列合计约 868 px。**这个数是被窗口最小宽度倒推出来的**：Tk 的 Treeview 在窗口
变窄时只会把多出来的余量摊掉，**不会**把列缩到设计宽度以下 —— 加起来比控件宽就直接
截掉右边，而且没有横向滚动条。窗口最小 940 px、内容区约 880，所以设计宽度必须压在
880 以内；默认窗口（1200）下这些列被 stretch 摊开，看起来更松。

**表头上方加一条组头**：九列数字分三组，`时间（秒）` 压在最快–最慢三列上方、
`3BV/s` 与 `stnb` 各压在自己那三列上方。不然三对「最快/平均/最慢」「最高/平均/最低」
只看表头分不清哪三列是哪个指标。组头位置按 Treeview 的**实际**列宽算（bbox），
不能用设计宽度——列宽随窗口变，硬算会整整偏一列。

**不加** NF 局数列、不加当天 PB 数、不加"距上次多少天" —— 一屏看完优先。
NF 局数放在底部明细条里（一句话里带出来），也更详细地出现在导出的总结里。

### 5.2 交互

- **级别单选**（Pill，沿用 `LEVEL_ACCENT`）——三级的 BV 分布完全不同，没有"全部"。
  默认**高级**，且按钮真的点亮（`_build_daily` 末尾就调 `set_daily_level`；
  以前默认画初级、三个按钮全灰，看不出当前在哪一级）。
- **点一行** → 底部明细条写当天摘要（局数、最快、最慢、跨度）。
- **双击一行** → 打开当天局列表（见 5.3）。
- **右键一行** → 复制当天总结（见 5.5）。
- 表头点击排序沿用 `Table` 现成能力。

### 5.3 当天明细：对话框（已定）

**对话框**。双击一天 → 弹出表格，列出当天每一局：时刻 / time / BV / 3BV/s / stnb /
风格 / 距当前 PB，双击某局播放。页面本身干干净净，不与主表抢高度。

行数少的当天不弹大框：表格行数 = min(max(局数, 3), 14)，1 局的当天只有一个三行的小窗；
超过 14 行滚动看（单日最多见过 578 局）。

（备选方案「页面内下分区」已否：500 px 的内容区装两个表，两边都看不了几行。）

### 5.4 空态与边界

| 情况 | 表现 |
|---|---|
| 该级别一局都没有 | 表格空，中间一行「这个级别还没有完成局」 |
| 未扫描完 | 沿用 `lbl_boot` 遮罩 |
| 有局但 `t0` 走了 mtime 兜底 | 状态栏「N 局按文件时间归日」，不进页面正文 |
| 今天没有完成局 | 「今日总结」给出提示，不弹空图 |
| 剪贴板被别的程序占着 | 状态栏报「图片复制失败」，不静默失败 |

### 5.5 当日 / 今日总结（v0.26.0）

两条入口，同一份数字：

| 入口 | 范围 |
|---|---|
| 每日页**右键某一天** | 那一天、当前级别的记录 |
| 概览页「最近完成局」右上角**今日总结**按钮 | 今天有局的**所有**级别，并在一张图 / 一段文字里 |

两种形态：

- **文本**：直接 `clipboard_append`，粘到聊天窗口就是几行纯文字。
  ```
  2022-12-14 · 中级 · 107 局
  01:10:47 – 13:58:55（12 小时 48 分）
  NF 26（24%）
  时间（秒）：最快 24.580 / 平均 36.784 / 最慢 48.660
  3BV/s：最高 2.558 / 平均 1.780 / 最低 0.989
  stnb：最高 35.392 / 平均 23.392 / 最低 10.908
  —— YuanshenToolbox v0.26.0
  ```
  标签用表里同名的那三个词（**最快 ≠ 最高**），不另造词。
- **图片**：PIL 画一张浅色卡片，2 倍像素渲染，字体用程序自带的 MiSans，
  写进剪贴板用 `CF_DIB`（ctypes 直调 Win32，不引 pywin32）。**不截窗口**：
  截图带边框、跟 DPI 走、窗口被挡住就废。

图片的版式：

- 卡片右侧一张角色贴纸（v0.27.0）：**略高于卡片**、下沿齐平、间隔 18。贴纸宽高比
  1.44，与卡片等高时整张图仍是 3.5:1，所以让它高出卡片一截，把比例拉到 2.5–2.9；
  高度按**目标比例**反推（`_mascot_h`），再用素材原生高度封顶 —— 素材只有 988 px。
  卡片在内容里竖直居中，不然卡片上方会空出一条粉底、重心明显偏下。
- **只有一级的今日卡套用单日卡版式**：矩阵退化成一行，卡片又矮又宽，怎么调贴纸都是
  3.2:1；而「今天只打了高级」恰恰是最常见的情况。这一级本来就是一张单日卡，
  套过去还能多给出起止与 NF。
  白底图在入库时归一化成纯白，绘制时按**乘性混合**贴 —— 白的地方正好变成页底色，
  不用抠图，半透明的花瓣边缘也不会留在白方块里。
- 单日卡片宽 540（含贴纸渲染 2526×999）：标题 `2022-12-14` + 级别色小标签 + 右上角局数；
  第二行起止 / 跨度 / NF；中间一张三行表（时间 / 3BV/s / stnb × 最好 / 平均 / 最差）；
  底部左边程序版本、右边生成时刻。
- 今日卡片宽 756（含贴纸渲染 3012×1036）：标题 + 「共 N 局」，下面一行级别色标签，然后是一张矩阵 ——
  行是级别，列是三组指标 × 三格。
- **表头只能写「最好 / 平均 / 最差」**：一行表头要同时覆盖三行指标，而时间越小越好、
  3BV/s 与 stnb 越大越好，写「最快」就对后两行不成立。文本形态里没有这个约束，
  所以照旧用最快 / 最高。
- 三级的平均时间不混算，**今日卡片不出一行「合计」**，合计局数放在标题右边。

## 6. 口径（写死，防止以后漂）

1. **一天 = 本地时区 00:00–24:00，按开始时刻归日**。跨午夜的局归开始那天（全量 15 局）。
2. **起** = 当天最早一局的开始；**止** = 当天最晚一局的结束。
3. **平均 = 算术平均**（与 Arbiter 一致，见 §1 反算证据）。
4. 只含**完成局**、只含**标准模式** —— 沿用 `scan()` 既有的两道过滤，每日页不另设口径。
5. **不过滤 3BV 门槛**。小盘局算进去，最快/最高会偏"好看"，这是"当天真实发生了什么"，
   与 Arbiter 同口径。
6. 级别互不混合，一次只看一级。
7. 元扫雷与阿比特的局**合并统计** —— 同一个人的成绩，按软件分开反而看不到连续进步。

## 11. 实现要点（与方案草图的差异）

1. **表头上方加了一条组头。** 列里的「最快/平均/最慢」与「最高/平均/最低」只看表头
   分不清哪三列属于时间、哪三列属于 3BV/s（v0.26.0 又有 stnb 三列）；组头把九列数字
   分成三组，各压在自己那三列上方。
2. **组头位置按实际列宽算，不能用设计宽度累加。** 列是 stretch 的，实际宽度取决于
   窗口；实现用 `Treeview.bbox()` 取实际列宽，并挂在表格的 `<Configure>` 上重画。
3. **「最近完成局」的时间列也换成录像内时刻**（方案只提了日期列）。同一行里日期来自
   录像、时间来自文件 mtime，拷贝过的录像会自相矛盾。排序键一起换成 `t0`（取不到退回 mtime）。
4. **明细有两条入口**：双击某天，以及底部明细条上的「当天明细」按钮 —— 只靠双击
   等于把功能藏起来，选中一行后按钮就亮，更像能点的东西。
5. **跨午夜的局**：去重后 22723 局里，开始与结束不在同一天的只有 **15 局**（全是阿比特，
   占 0.07%）。归日按开始时刻，这 15 局都算在开始那天。

6. **列宽是被最小窗口倒推的，不是"看着好看"定的。** v0.26.0 加到十三列时先按 1030 px
   的内容区算，结果窗口一拉窄就有列被裁掉 —— Tk 的 Treeview 只摊余量、不缩列，
   也没有横向滚动条。现在设计宽度合计 868 px，压在最小窗口的内容区（约 880）以内。
7. **今日卡片的表头只能写「最好 / 平均 / 最差」。** 一行表头要同时覆盖时间、3BV/s、stnb
   三行指标，而时间越小越好、另两项越大越好；写「最快」对后两行不成立。文本形态没有
   这个约束，所以照旧写最快 / 最高 —— 同一个功能两种形态用了两套词，是有意的。
8. **分组标题压的是中间那一列的「文字」，不是列方框。** 子表头是右对齐的，按列方框居中
   会让标题整体偏左十几像素，看着像压在最差那列上（第一版就是这样，量像素才发现）。
9. **图片不截窗口。** 截图带边框、跟 DPI 走、被别的窗口挡住就废；改用 PIL 按 2 倍像素画，
   字体用随程序打包的 MiSans，别人机器上不会掉字。
