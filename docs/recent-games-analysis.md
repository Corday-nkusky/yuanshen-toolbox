# 「最近完成局」改成 PB 对比 + 扩容到近三天：性能分析

> 已按第 8 节的参数落地（v0.21.0）。实测结论在实现之后又复核过一遍，没有变化。

调查对象：主页「概览」页签里那张表。方案是删掉「录像文件」列、换成与当前 PB 的比较，
行数从 10 行改成「最近 100 局」与「最近三天」取较多。

**结论：性能不是问题。** 真实数据（22558 局）上，144 行（本机近三天的实际局数）的
整表重画是 9~10 ms，和现在 10 行的 7~8 ms 同一个量级；PB 比较本身的开销测不出来。
唯一需要设防的是「近三天」这个按文件时间取窗口的规则在**批量导入**时会退化到万级行，
那一种情况要加硬上限。

下文所有数字都是【实测】，本机（Windows / Python 3.13 / Tk 8.6），
数据是用户真实录像（`%APPDATA%\Metasweeper3.3.4\replay` + `D:\扫雷\replays` +
`D:\扫雷\replays2`，共 22559 个文件、22558 个完成局）。复现脚本见文末。

---

## 1. 现在这 10 行是怎么来的

- 渲染入口只有一处：`app.py:4249` `render_recent()`，由 `_on_scanned()` 在
  `app.py:4127` 调一次。切页签不重画，所以它只在「扫描完成且数据真的变了」时跑。
- 数据源是 `self.games`（扫描时已经解析好的 dict 列表），每次现排一次
  `sorted(..., key=mtime, reverse=True)[:10]`。
- 唯一成本 = 全量排序 + 10 行插进 Treeview。

所以改版的成本就是这三项的变化：**排序（不变）+ 每行多一次 PB 查表（可忽略）+
插入行数（线性增长）**。

## 2. 三个改动分别花多少

### 2.1 排序：6.5 ms，且不随行数变

全量 22558 局按 `mtime` 排序，min 6.47 ms / median 6.76 ms（5 次）。
取前 N 行不影响这段开销 —— 改成 100 行还是近三天，排序都是这个数。

想省的话可以缓存排序结果（扫描结束后排一次），但 6.5 ms 不值得为它加状态。

### 2.2 换成 PB 比较：开销测不出来

- 建索引（`(级别, BV) → PB 行`，全PB / NF PB 各一份）：0.048 ms。
- 每行一次 dict 查表 + 拼一个字符串：1000 行合计 1.07 ms。

对照组实测（同样 10 行，同一窗口，7 次取中位数）：

| 配置 | min / median |
|---|---|
| 10 行**带** PB 比较 | 7.2 / 8.4 ms |
| 10 行**不带** PB 比较 | 8.3 / 9.8 ms |

带比较反而「更快」—— 说明差异在噪声里。**这一项不需要为性能做任何妥协。**

### 2.3 行数：约 0.017 ms/行，整表重画实测

在真实 `App` 窗口里（窗口可见，含 `update()` 强制重绘），`sorted → 组装 → Treeview.set_rows`：

| 行数 | min / median | 说明 |
|---|---|---|
| 10（现状） | 7.2 / 8.4 ms | 基线 |
| 144 | 9.3 / 10.4 ms | **本机近三天的实际局数** |
| 500 | 14.9 / 16.8 ms | 一般上限 |
| 1000 | 23.1 / 26.5 ms | |
| 2000 | 40.2 / 44.4 ms | |
| 5000 | ~95 ms | 只在退化时出现 |
| 22558（全部） | ~400 ms | 退化最坏情况 |

边际成本约 0.017 ms/行。人眼能察觉的卡顿门槛大约在 100 ms，也就是**要到 5000 行才开始有感**。

### 2.4 顺带测的交互项

- **点表头排序**（用户点一次 = 重排 + 全量重画）：1000 行 8.4 ms，3000 行 26.7 ms。
- **滚动**：1000 行滚到底再回顶，75 ms / 轮（一次滚动约 4 ms）——Tk 的 Treeview
  不做虚拟化，但 1000 行仍然顺。

## 3. 端到端：扫描完成 → 整个概览页刷完

这才是用户实际感觉到的那一下（卡片 + 最近局 + PB 表 + 前端成绩，全部在一个 Tk 空闲周期里）：

| 最近局行数 | 整页刷新耗时 |
|---|---|
| 10（现状） | 46 ms |
| 100 | 50 ms |
| 144 | 52 ms |
| 1000 | 69 ms |

本机一次热缓存全量扫描本身就是 297~320 ms（22559 个文件）。也就是说改成近三天之后，
**扫描完到界面刷新完，总共多 6 ms**，占比 2%。

## 4. 内存

每行约 0.85 KB（`dict(g)` 复制 + 格式化字段）：

| 行数 | 额外内存 |
|---|---|
| 144 | 0.1 MB |
| 1000 | 0.8 MB |
| 22558 | 19.1 MB |

可以忽略。

## 5. 唯一真正的风险：按 mtime 取窗口会退化

「近三天」是按文件修改时间筛的。正常玩一局落一个文件，这个窗口很准；但有两种情况会把
窗口撑成万级：

1. **批量导入**：把别人的存档包解压/拷进来 —— 解压出的文件 mtime 是解压那一刻，
   几千个文件全部落进「近三天」。
2. **改系统时间 / 从镜像恢复**：大量文件的 mtime 会聚到一起。

实测退化后果：22558 行 400 ms 重画 + 19 MB 常驻，而且表格本身也失去意义
（用户不会去翻两万行）。这个场景还会**每次扫描都触发**（自动刷新发现目录变了就重扫重画）。

**所以要加一个硬上限。** 按时间倒序截断，最新那部分不受影响。

上限取多少：本机历史单日最高 575 局（2023-03-26），三天连打理论上能到 1500 上下。
建议 **2000**（44 ms / 1.7 MB，完全无感）；如果更在意表格「可翻」而不是「全」，1000 也够。

## 6. 落地时会撞到的三个坑（不是性能问题，但会让功能错）

这几条是我读代码时确认的，不改就会出错：

1. **调用顺序错了会用上一轮的 PB。** `_on_scanned()` 里 `render_recent()` 在
   `app.py:4127`，而 PB 行要到 `app.py:4133` 的 `_recompute_pb()` 才算出来。
   直接在里面读 `self.pb_rows`，首次扫描拿到的是空列表，之后拿到的是上一次的结果。
   要么把 `render_recent()` 挪到 `_recompute_pb()` 之后，要么改用 `pb_local_rows` 建索引。
2. **网站 PB 是后到的，到了必须重画一次。** `_on_site_pb()` → `_site_pb_changed()`
   （`app.py:2989`）会更新 `self.pb_rows`。如果比较列不跟着重画，用户会看着
   「本地 PB」的差距，直到下一次扫描才变。补一次 `render_recent()` 的代价是
   9~26 ms，可以忽略。
3. **删掉「录像文件」列会把「自动撑满」的那一列也删掉。** `Table.__init__`
   （`app.py:557`）只给 `file / path / player / why` 打开 `stretch`，删了 file 列
   而新列不在这个名单里，表格右侧会留一条空白。新列要么加进那个元组，要么改成
   「最后一列 stretch」。

另外确认过：双击播放、右键菜单都不依赖「录像文件」这一列 —— 它们读的是行数据里的
`path`（`Table._path_of`），删列不影响这两个功能。

## 7. 口径：「和当前 PB 比较」具体跟哪个 PB 比

这决定的是列里那个数字对不对，不是性能。现有 PB 是两张榜（`core.build_pb_rows`）：
全PB 和 NF PB，各自在子集内取最快；再和网站 PB 合并（`core.merge_site_pb`）。
三种可选口径，成本完全一样（都是查一次 dict）：

| 口径 | 含义 | 问题 |
|---|---|---|
| 按行风格取对应榜（推荐） | NF 局比 NF PB，FL 局比全PB | 和 PB 页签看到的数字能对上 |
| 一律比全PB | 所有局比「同 BV 最快」 | NF 局和 FL 的 PB 比，差距没有可比性 |
| 一律比 NF PB | 只和禁插旗的 PB 比 | FL 局几乎所有行都是「比 PB 慢」 |

建议第一种：比较列和 PB 页签的口径一致，用户来回看不会出现两个数。
行本身正好是 PB 记录时标「PB」而不是「+0.000 s」（时间相同也可能是另一局，路径相同才是同一局）。

还有一个语义后果，你已经接受了但值得写在 CHANGELOG 里：PB 会变，所以**历史行的差距会
跟着变**。今天显示「+0.532 s」的那局，等破了自己的 PB 之后会变成「+0.900 s」——
这不是 bug，是这一版的定义。

## 8. 建议的落地参数

```
行数 = max(100, 近三天局数)，硬上限 2000
PB 比较 = 按行风格取对应榜（全PB / NF PB），与 PB 页签同口径，含网站 PB
渲染时机 = 扫描完成后（在 _recompute_pb 之后）+ 网站 PB 到达后各一次
```

代价（本机实测）：典型 144 行多 6 ms；上限 2000 行多 37 ms；内存最多 1.7 MB。

## 9. 我没验证的部分

- **只有这一台机器。** DPI 缩放（`sc()`）、老 CPU、机械硬盘都没测。我的判断是
  插入行数的成本主要由 Tk 的布局决定、跟磁盘无关，但跨机器我没实测。
- **没在打包后的 exe 里跑。** 上面的数字全是源码跑（`App` 类同一个窗口、同一个
  `_on_scanned` 数据流），exe 是同一个解释器 + 同一套 tk，理论上无差别，但我没有实测对照。
- **退化场景是构造的，不是撞上的。** 「22558 行」这一栏是把全部局当作都在三天内塞进表格
  测出来的，真实用户有没有这么干过我无从判断；公开版会不会有人解压一个大存档包，
  只能靠上限兜住。
- **网站 PB 后到的那次重画没做端到端计时**，只测了单次 `render_recent` 本身的耗时。
- **「近三天」按 mtime 而不是录像内部时间**，这一点沿用了现有「日期/时间」两列的口径
  （`core.scan` 里 `date` 也来自 mtime），没有改成读录像内的对局时间。要不要改是另一个
  议题：改的话每局都要重新解析，冷扫描会慢一个量级。

### 复现方式

探针脚本在 `_probe/`（不进仓库）：

```
# 1. 把真实缓存复制一份，不碰用户数据目录（关键）
mkdir -p "$TEMP/ytb-bench"
cp "$APPDATA/Metasweeper3.3.4/YuanshenToolbox-data/scan-cache.db" "$TEMP/ytb-bench/"

# 2. 数据层：排序 / PB 索引 / 组装 / 近三天窗口分布
MS_PB_DATA_DIR="$TEMP/ytb-bench" python _probe/bench_recent.py

# 3. Treeview 纯插入成本（可见窗口 / 不可见窗口各一份）
"/c/Users/TANGWENJIAN/AppData/Local/Programs/Python/Python313/python" _probe/bench_tree_visible.py

# 4. 真实 App 窗口里的整表重画 + 整页刷新（要 ms_toollib，用打包 venv）
MS_PB_DATA_DIR="$TEMP/ytb-bench" /tmp/ytb-build/Scripts/python.exe _probe/bench_stable.py
MS_PB_DATA_DIR="$TEMP/ytb-bench" /tmp/ytb-build/Scripts/python.exe _probe/bench_app_worst.py
```
